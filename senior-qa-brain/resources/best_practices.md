# 最佳实践

## 1. 测试用例设计

### 1.1 设计原则
- 独立性：每个用例独立可执行，不依赖其他用例
- 可重复性：相同条件下执行结果一致
- 可验证性：预期结果明确可判定
- 完整性：覆盖所有功能点和边界条件

### 1.2 用例结构
- 用例ID：唯一标识，便于追踪
- 测试点：明确测试目标
- 前置条件：执行前的系统状态
- 测试步骤：详细操作步骤
- 预期结果：明确的判定标准
- 优先级：P0-P3分级

### 1.3 命名规范
- 模块名_功能名_测试场景
- 使用下划线分隔
- 避免特殊字符

## 2. 自动化测试

### 2.1 选择策略
- 优先自动化P0-P1级别用例
- 优先自动化回归频繁的用例
- 优先自动化稳定的功能模块
- 避免自动化不稳定的功能

### 2.2 API 自动化代码规范
- 使用 Request Builder、API Client、Fixture/Data Factory、Response Validator 分层
- 请求中的 URL、Query、Header、Cookie、Body 分离
- 认证值从测试环境读取，Token、Cookie 和密码不得写入代码或报告
- 断言按 HTTP 状态码、业务码、响应 Schema、关键业务字段和数据变化分层
- 外部服务和数据库请求设置明确超时；数据库验证默认读取主库或具备读后校验机制
- 不用固定共享数据验证支付、领取、绑定等一次性状态场景

### 2.3 维护策略
- 定期更新失效用例
- 建立用例执行监控
- 及时修复失败用例
- 保持测试代码与产品代码同步

## 3. 测试执行

### 3.1 执行策略
- 按优先级执行：P0→P1→P2→P3
- 冒烟测试：验证核心功能
- 回归测试：验证改动影响
- 探索性测试：发现潜在问题

### 3.2 缺陷管理
- 缺陷描述清晰完整
- 复现步骤详细可操作
- 缺陷分类准确合理
- 缺陷状态及时更新

### 3.3 测试报告
- 覆盖测试范围和结果
- 包含缺陷统计和分析
- 提供风险评估和建议
- 格式清晰易于阅读

## 4. 测试环境

### 4.1 环境管理
- 保持测试环境与生产环境一致
- 定期清理测试数据
- 备份重要测试数据
- 建立环境文档

### 4.2 数据管理
- 使用真实数据格式
- 覆盖各种数据场景
- 数据隔离避免干扰
- 定期更新测试数据

## 5. 协作沟通

### 5.1 需求沟通
- 参与需求评审
- 明确需求边界
- 记录疑问和风险
- 确认需求变更

### 5.2 开发沟通
- 参与技术方案评审
- 了解实现细节
- 同步测试进度
- 及时反馈问题

### 5.3 产品沟通
- 确认需求理解
- 验证产品效果
- 反馈用户体验问题
- 参与产品验收

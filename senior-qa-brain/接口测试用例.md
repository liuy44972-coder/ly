# 用户接口业务测试用例

## 1. 测试范围

| 接口名称 | 方法 | 路由 | 业务作用 |
|---|---|---|---|
| 同步用户信息 | POST | `/api/user/sync` | 同步用户存档，替代 message 接口 |
| 解绑 v2 | POST | `/api/user/unbinding/v2` | 解绑用户并同步用户信息 |
| 重置用户 v2 | POST | `/api/user/resetUser/v2` | 重置用户并同步用户信息 |

> 公共 Header、Query 参数及部分 Body 参数在当前文档中不可见，本文统一使用“有效公共参数”表示，具体字段待接口文档补充。

## 2. 公共请求数据

### 2.1 嵌套结构

```json
{
  "increment": 105,
  "ts": 1786435198,
  "payload": {
    "items": {
      "10001": 20,
      "10002": 3
    },
    "stage": 15,
    "chapter": 3,
    "level": 8,
    "cust": {
      "PlayerModel_KEY": {
        "name": "Player",
        "energy": 30
      }
    },
    "mapid": 2001,
    "playtime": 3600,
    "taskLength": 25
  }
}
```

### 2.2 扁平兼容结构

```json
{
  "increment": 105,
  "ts": 1786435198,
  "items": {
    "10001": 20,
    "10002": 3
  },
  "stage": 15,
  "chapter": 3,
  "level": 8,
  "cust": {
    "PlayerModel_KEY": {
      "name": "Player",
      "energy": 30
    }
  },
  "mapid": 2001,
  "playtime": 3600,
  "taskLength": 25
}
```

## 3. 业务规则

1. `items` 为道具数量字典，按整体覆盖处理，不是增量加减。
2. `stage`、`chapter`、`level`、`mapid`、`playtime`、`taskLength` 为直接覆盖字段。
3. `cust` 只覆盖本次上传的一级 key。
4. 防回退校验顺序为：先比较 `stage`，再比较 `mapid`，当 `mapid` 相等时再比较 `taskLength`。
5. 任一回退或非数字值均拒绝，返回 `code: 654`，`data` 为失败字段名。
6. 客户端 `increment` 小于服务端当前值时拒绝存档，返回 `code: 632`，`data: "用户数据冲突"`。
7. 成功响应包含服务端当前存档、`increment`、`commit`、响应时间戳、邮件和活动等重新计算数据。
8. 公共副作用和各接口专属更新以服务端最终业务规则为准。

# 4. 同步用户信息接口

## TC001：同步完整合法用户存档

- **前置条件**：用户已登录；公共 Header、Query 参数有效；服务端当前 `increment` 小于请求值。
- **请求步骤**：POST `/api/user/sync`，携带完整合法嵌套 Body。
- **预期结果**：返回成功业务码 `200`；存档字段正确保存；返回 `increment` 等于请求值；返回 `commit`、`ts`、`mails`、`activities` 等公共响应字段；邮件和活动为服务端重新计算结果。
- **优先级**：P0
- **测试类型**：业务功能测试
- **自动化**：✅

## TC002：同步最小合法存档

- **前置条件**：用户已登录，公共参数有效。
- **请求步骤**：仅传递必要公共字段及四个必传字段 `increment`、`stage`、`mapid`、`taskLength`，不传可选存档字段。
- **预期结果**：请求成功；必传字段正确保存；未传可选字段按接口规则处理，不得异常清空已有数据。
- **优先级**：P1
- **测试类型**：业务边界测试
- **自动化**：✅

## TC003：同步扁平兼容结构

- **前置条件**：服务端启用扁平结构兼容。
- **请求步骤**：使用扁平结构请求 `/api/user/sync`，数据与嵌套结构等价。
- **预期结果**：请求成功；字段解析及最终存档与嵌套结构一致；不将 `payload` 作为业务字段保存。
- **优先级**：P1
- **测试类型**：兼容性测试
- **自动化**：✅

## TC004：缺少必传字段

- **前置条件**：用户已登录，其他字段合法。
- **请求步骤**：分别删除 `increment`、`stage`、`mapid`、`taskLength` 后请求接口。
- **预期结果**：请求失败；不应更新用户存档。
- 缺失 `increment` 返回错误码 `632`；缺失 `stage`、`mapid` 或 `taskLength` 返回错误码 `654`；错误信息明确指出缺失字段。
- **优先级**：P0
- **测试类型**：必填参数校验
- **自动化**：✅

## TC005：increment 小于服务端当前值

- **前置条件**：服务端当前 `increment` 为 `105`，请求值为 `104`。
- **请求步骤**：携带其他合法数据请求同步接口。
- **预期结果**：返回 `code: 632`，`data: "用户数据冲突"`；服务端所有存档字段保持不变，不得部分写入。
- **优先级**：P0
- **测试类型**：版本冲突与防回退测试
- **自动化**：✅

## TC006：increment 等于当前值

- **前置条件**：服务端当前 `increment` 为 `105`。
- **请求步骤**：使用 `increment: 105` 提交合法存档。
- **预期结果**：是否允许覆盖需符合最终接口约定；不得重复自增或产生部分更新。当前规则未明确，标记待确认。
- **优先级**：P1
- **测试类型**：版本边界测试
- **自动化**：✅

## TC007：increment 大于当前值

- **前置条件**：服务端当前 `increment` 为 `105`，请求值为 `106`。
- **请求步骤**：提交合法存档。
- **预期结果**：返回 `code: 200`；服务端当前版本更新为 `106`；查询接口返回最新存档。
- **优先级**：P0
- **测试类型**：版本更新测试
- **自动化**：✅

## TC008：stage 回退

- **前置条件**：请求 `stage` 小于服务端当前值。
- **请求步骤**：提交其他合法字段。

- **优先级**：P0

- **自动化**：✅

- **自动化**：✅

## TC010：taskLength 回退

- **请求步骤**：请求同步接口。
- **预期结果**：返回 `code: 654`，`data: "taskLength"`；存档不变。
- **优先级**：P0
- **测试类型**：业务规则校验
- **自动化**：✅

## TC011：多个字段同时回退

- **前置条件**：`stage`、`mapid`、`taskLength` 均回退。
- **请求步骤**：请求同步接口。
- **预期结果**：按 `stage → mapid → taskLength` 顺序校验；返回 `code: 654`，`data: "stage"`；不得返回其他字段作为首个失败字段。
- **优先级**：P1
- **测试类型**：校验优先级测试
- **自动化**：✅

## TC012：stage 上升但 mapid 回退

- **请求步骤**：提交同步请求。
- **预期结果**：返回 `code: 654`，`data: "mapid"`；不能因为 stage 上升而允许 mapid 回退。
- **优先级**：P1

- **自动化**：✅

## TC013：stage、mapid 相等时 taskLength 回退

- **前置条件**：`stage`、`mapid` 与服务端相等，`taskLength` 回退。
- **请求步骤**：提交同步请求。

- **自动化**：✅

## TC014：防回退字段为非数字

- **前置条件**：用户已登录。
- **请求步骤**：分别将 `stage`、`mapid`、`taskLength` 设置为字符串、对象、数组、布尔值和 `null`。
- **预期结果**：任一非数字值均拒绝；返回 `code: 654`；按照校验优先级返回失败字段；不得写入非法值。

## TC015：items 整体覆盖

- **请求步骤**：携带部分 `items` 请求同步接口。
- **预期结果**：请求成功；服务端按整体覆盖规则处理；不得将数量进行增量累加；未上传道具的处理方式待字段更新规则确认。

# 5. 解绑 v2 业务用例

## TC021：解绑用户并同步合法信息

- **前置条件**：用户已登录，存在有效存档，公共参数有效。
- **请求步骤**：POST `/api/user/unbinding/v2`，携带合法同步数据；随后调用 `/user` 查询状态。
- **预期结果**：解绑成功；session 被清理；公共副作用按规则执行；原 session 访问需登录接口失败；不影响其他用户数据。
- **优先级**：P0
- **测试类型**：核心业务流程测试
- **自动化**：✅

## TC022：解绑请求触发同步校验失败

- **前置条件**：构造 `stage`、`mapid` 或 `taskLength` 回退数据。
- **请求步骤**：请求 `/api/user/unbinding/v2`。
- **预期结果**：返回 `code: 654` 和失败字段；解绑动作是否执行必须符合事务规则；不得出现 session 已清理但存档更新失败的非预期部分状态。
- **优先级**：P0
- **测试类型**：事务一致性测试
- **自动化**：✅

## TC023：重复解绑

- **前置条件**：用户已成功解绑一次。
- **请求步骤**：使用原 session 或重复请求再次解绑。
- **预期结果**：不能重复清理或产生异常副作用；返回结果符合幂等规则；不得影响重新绑定后的新用户。
- **优先级**：P1
- **测试类型**：幂等性测试
- **自动化**：✅

# 6. 重置用户 v2 业务用例

## TC024：重置已有用户

- **前置条件**：用户已有道具、关卡、活动、邮件、自定义存档等非默认数据。
- **请求步骤**：POST `/api/user/resetUser/v2`，携带合法同步数据；重置后查询用户信息。
- **预期结果**：先整体重置为默认用户，再执行公共同步链路；除明确保留的账号级字段外，玩法数据清零或恢复默认；返回新用户状态。
- **优先级**：P0
- **测试类型**：破坏性业务流程测试
- **自动化**：✅

## TC025：重置前后数据对比

- **前置条件**：记录重置前完整用户数据。
- **请求步骤**：执行重置并查询 `items`、`stage`、`chapter`、`level`、`mapid`、`playtime`、`cust`、邮件和活动。
- **预期结果**：玩法字段符合默认值；旧道具、旧进度、旧自定义数据不应错误保留；账号级字段按保留规则保留。
- **优先级**：P0
- **测试类型**：数据清理测试
- **自动化**：✅

## TC026：重置后重新同步

- **前置条件**：用户已完成重置并获得重置后的用户状态。
- **请求步骤**：使用重置后的用户状态提交一次合法同步。
- **预期结果**：新用户可以正常同步；新存档不会与旧用户数据混淆；版本号和 commit 按新用户规则处理。
- **优先级**：P0
- **测试类型**：业务链路测试
- **自动化**：✅

## TC027：重复重置

- **前置条件**：用户已完成一次重置。
- **请求步骤**：再次调用 `/api/user/resetUser/v2`。
- **预期结果**：不会恢复旧数据；重置后的默认数据保持一致；重复操作的幂等行为符合接口约定。
- **优先级**：P1
- **测试类型**：幂等性测试
- **自动化**：✅

## TC028：重置与同步并发

- **前置条件**：同一用户同时发起重置和同步请求。
- **请求步骤**：并发调用 `/api/user/resetUser/v2` 与 `/api/user/sync`。
- **预期结果**：最终状态符合服务端定义的事务顺序；不得出现旧存档覆盖重置结果；不得出现部分重置、部分旧数据残留。
- **优先级**：P0
- **测试类型**：并发与事务一致性测试
- **自动化**：✅

- **优先级**：P1
- **测试类型**：公共副作用测试
- **自动化**：✅

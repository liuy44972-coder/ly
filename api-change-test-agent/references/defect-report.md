# 缺陷单输出规范

## 1. 何时使用

仅当 [failure-triage.md](failure-triage.md) 判定为「服务真实缺陷」时使用：文档与断言都正确、同请求可稳定复现、实际响应不符合契约。

其他归因不走本模板：断言写错给修改建议，前置数据不满足标 `blocked`，契约变更先报冲突。

## 2. 模板

```text
标题：[<服务>] <接口> <一句话现象>（期望 X，实际 Y）
环境：<profile> / <API_BASE_URL 脱敏后域名> / <客户端版本>
前置：账号类型、单据状态、资源状态（说明是否一次性）
复现步骤：
  1. <请求方法与路径，含 query 关键项，不含 Token>
  2. <body 关键字段>
  3. <可选的第二次请求，用于证明幂等或状态异常>
期望结果：HTTP <status> + code=<业务码> + <字段断言>
实际结果：HTTP <status> + code=<业务码> + <字段实际值>
复现概率：<n/n>
证据：Allure 用例 ID / requestId / 日志片段（脱敏）/ 截图路径
影响面：涉及用户范围、是否阻塞发版、是否有数据副作用
初步归因：服务缺陷（附排除项：环境、鉴权、前置数据、断言均已排除）
建议：<修复方向，不替开发做实现决定>
```

## 3. 严重级判定

| 级别 | 判定标准 |
|---|---|
| P0 | 数据错乱、资损、越权可复现，或核心链路完全不可用 |
| P1 | 主流程某个状态不可达、重复发放或漏发，无绕行方案 |
| P2 | 异常场景返回错误码/字段不符，主流程可用 |
| P3 | 文案、日志、非关键字段不符 |

## 4. 证据要求

- 必须带用例 ID 与脱敏后的请求/响应，保证开发不复跑就能定位；
- 一次性资源（兑换码、单据、邮件）只能提供一次证据，提交前先确认响应已留档；
- 不得粘贴完整响应体、Token、Cookie、`sign`、用户隐私字段；
- 无法稳定复现的，标「偶现」并附出现次数，不升级为 P0/P1。

## 5. 禁止

- 没有证据就断言「这是 bug」，或把环境、鉴权、前置数据问题写成服务缺陷；
- 为了证明缺陷去改断言、改用例、改生产代码；
- 在同一份缺陷单里混入多个不相关现象，一单一事。

# 写用例与写脚本的项目约束

阶段五的细则集中在这里；主文件只保留每次都要执行的硬约束。

## 断言写法清单

1. 断言统一用 [helper/assertions.js](../../../helper/assertions.js) 的 `check(actual, '断言说明')`，让断言进入 Allure；示例与防刷屏规则见 [allure.md](allure.md)。
2. 成功场景：HTTP 状态码、业务码、关键字段、数据类型都要断言；不用「响应存在」代替业务断言。
3. 异常场景：断言实际 HTTP 状态码、业务码与错误字段。
4. 变更字段必须有正向断言；删除字段必须有「不存在」断言。
5. 失败信息自带脱敏后的响应片段，保证不复跑也能定位。
6. 文案与强度一致：label 里的「非空 / 包含 / 大于 / 等于」必须与 matcher 和实测值对应；对不上时补断言或改文案，禁止用模糊表述掩盖弱断言。

## 写操作用例的数据还原

适用于「改值后能改回来」的接口，与一次性资源区分：

- 优先原值写回：先查询当前值，再按原值提交，验证「能写 + 不产生多余字段」；
- 必须提交不同值时，值要基于查询到的真实结构改造（如改一个标量字段），不得手写结构：服务端常对 `cust` 这类二进制字段做 JSON round-trip 校验，手写结构会被 `606`（参数取值错误）拒绝；
- 提交后用 `try/finally` 还原写入前的原值，并在报告中保留「修改 → 还原」两次请求；还原失败要显式报出，不能静默；
- 选字段时避开计数、进度、货币、限次类字段，优先选仅影响展示或可安全回滚的标量。

## 文本用例与脚本的分工

- 文本用例只写契约与用例：请求方法/路径、参数、预期状态码、业务码、关键字段与边界，不写 spec 路径、门控变量、fixture 键值、运行命令；
- 每条文本用例对应一个独立 Jest `test`，测试名以唯一用例 ID 开头，上方保留中文用例备注；
- 仅文字无自动化的用例在文档中标注 `no-auto`，并在索引里保留该 ID；
- 用户只要「用例」时，按 [text-case-design.md](text-case-design.md) 的 4 节骨架输出，不附工程章节，也不生成报告。

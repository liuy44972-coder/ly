# 文本用例：ID 规范、文档骨架与自评审

## 用例 ID 规范

- 格式：`TC-<模块>[-<子模块>]-NNN`；
- 同一接口跨目录复用时，ID 与语义必须一致；薄挂载不复制 ID；
- 冒烟目录的用例必须与本目录归属一致，分两种情形：①薄挂载复用需求目录的定义时，继承原 ID、不加 `SMOKE` 段，不算重号；②在本目录独立编写的冒烟用例，必须带 `SMOKE` 段区分（如 `TC-GM-QUERY-SMOKE-002`），且禁止与环境全量目录重号；
- 已知历史重号（如 `TC-GM-QUERY-002` 在 `mf- smoke` 与 `mf-all`/`mf序列化` 下表意不同）在改动相关文件时一并整改，不单独发起大规模重命名；
- 新增、删除、修改用例时，同一次改动内同步文字用例与 `tests/cases/接口及接口用例汇总.md`；
- 改动后自检：`npm run cases:check`（脚本 `scripts/check-case-index.js`），输出四类标记：`[DUP]` 同目录重复定义、`[MISSING]` Smoke 定义未登记索引、`[EXTRA]` 索引冗余、`[LEGACY]` 跨目录未薄挂载的存量重号。判定顺序：先看 `[DUP]`/`[MISSING]` 是否由本次改动引入（是则必须修），再看 `[EXTRA]` 是否为 no-auto 或环境未覆盖，最后把 `[LEGACY]` 作为存量单列，不混进本次结论。默认报告模式不阻塞，存量清理后改用 `--strict` 做门禁；

## 文字用例文档骨架

`tests/cases/<需求>接口用例.md` 是给人看的交付物，骨架固定：

```text
# <服务> XX 接口测试用例
## 1. 测试范围     接口表 + 服务归属 + 环境
## 2. 前置约定     请求头 / 请求体 / 成功判定
## 3. 用例明细     用例 ID | 场景 | 请求要点 | 预期结果
## 4. 未覆盖与待确认  原因 + 后续
```

规范：

- 只写契约与用例，**不写实现细节**：不列 spec 文件路径、门控变量名、fixture 键值表、运行命令、lint 说明；
- 用户明确要求「只要文本用例」时，按此骨架输出，不再附带工程化章节；
- 预期结果必须包含 HTTP 状态码、业务码、断言字段；被前置条件门控的用例在「场景」列注明前置；
- 实测得到的错误码标注「实测确认」，并进入第 4 节待确认项；
- 用例设计与优先级沿用 `senior-qa-brain` 的维度（前置、请求步骤、预期、优先级、自动化可行性），落到本文档时收敛成上面 4 节，优先级写进「场景」列；本 skill 不再重复定义用例设计规范。

## 文本用例自评审（进入阶段五前必须完成，输出三行：用例总数 / 缺口 / 待确认项）

| # | 检查项 | 不合格示例 |
|---|---|---|
| 1 | 每条用例有 ID、场景、请求要点、预期（HTTP + 业务码 + 断言字段） | 只写「返回成功」 |
| 2 | 变更字段有正向断言，删除字段有「不存在」断言 | 新增字段没出现在任何断言里 |
| 3 | 异常场景按适用性覆盖，不适用的写明理由 | 全标 required 或全标跳过 |
| 4 | 前置条件与门控写明，标注是否消耗一次性资源 | 兑换码用例没写「码会被消耗」 |
| 5 | 每个预期值标来源（文档 / 代码 / 实测确认） | 凭经验写 `691` |
| 6 | 不出现实现细节（spec 路径、门控变量、运行命令） | 用例表里混进 `REDEEM_ALLOW_REDEEM` |

自评审发现缺口时按「有疑问必须询问」处理：能自己从代码确认的先确认，确认不了的列入待确认再问用户，不得带着缺口进入阶段五。
